# AI Agentic Fraud Investigation & Next-Best-Action System (Prototype)

A working prototype of an AI agent that investigates suspicious transactions
over a knowledge graph, gathers evidence, scores risk transparently, and
recommends a policy-governed next-best-action — with full explainability and
a human-approval gate for high-impact actions.

> **Scope note, read first:** this was built as a single-environment
> prototype, not against a live TigerGraph cluster or the real IEEE-CIS
> dataset. Every piece of the architecture from the spec is implemented and
> runs end-to-end today; TigerGraph and the real dataset are swap-in points
> rather than faked. See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for
> exactly what's real vs. simulated, and the **Implementation report**
> section at the bottom of this file.

## 1. Problem statement

Investigate suspicious financial transactions using graph relationships
(shared devices/IPs/merchants), prior case outcomes, and fraud policy, then
recommend — never silently execute — the next best action, with every
conclusion traceable to specific evidence.

## 2. Architecture

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the full diagram and
component breakdown.

## 3. Technology stack

- **Backend:** Python, FastAPI, Pydantic, SQLite (case store + audit log)
- **Graph:** `networkx` in-memory graph (DEMO_MODE) implementing the same
  query interface as real TigerGraph GSQL queries provided in `tigergraph/`
- **RAG:** TF-IDF retrieval (`scikit-learn`) over policy & fraud-pattern docs
- **Agent:** explicit Python state machine (`backend/app/agent.py`), not a
  LangGraph/Agents-SDK black box — chosen so every transition is inspectable
  and unit-testable without a hosted agent framework dependency
- **LLM (optional):** Anthropic API for explanation phrasing; deterministic
  template fallback when no key is set
- **Frontend:** single-file HTML/JS dashboard, Tailwind (CDN) + vis-network
  (CDN) for graph visualization — no build step required
- **Tests:** `pytest`, 22 tests across risk engine, policy engine, graph
  engine, and the full agent state machine

## 4. Installation

## 5. Environment variables

See [`.env.example`](.env.example). Nothing is hard-coded; every secret and
threshold is read from the environment. The system runs fully with an empty
`.env` (all defaults apply, `DEMO_MODE=true`).

## 6. Dataset setup

`data/sample/` is generated by `scripts/generate_sample_data.py` and is
**synthetic**, shaped to match the column contract described in the spec
(transactions carry `bank_risk_score`, not a ground-truth `is_fraud` label).
See `data/sample/README.md` for the exact schema and how to point the
ingestion pipeline (`backend/app/graph_engine.py::load_from_csv`) at the real
IEEE-CIS/HHGOA files instead — it reads columns by name, not position, and
reports missing-column errors rather than assuming a layout.

## 7. TigerGraph setup (optional — real integration provided, not required to run)

```bash
gsql tigergraph/schema/schema.gsql
gsql tigergraph/gsql/queries.gsql
gsql "INSTALL QUERY ALL"
gsql tigergraph/loading/loading_job.gsql
gsql 'RUN LOADING JOB load_fraud_data USING
      customers_csv="data/processed/customers.csv",
      transactions_csv="data/processed/transactions.csv",
      closed_cases_csv="data/processed/closed_cases.csv"'
```

Then set `TIGERGRAPH_AVAILABLE=true` and the `TG_*` variables in `.env`, and
wire `pyTigerGraph` calls into `backend/app/graph_engine.py` (the method
signatures already match the installed queries 1:1 — see the comments in
`tigergraph/gsql/queries.gsql`). Without this, the system runs fully against
the in-memory graph.

## 8. GSQL installation

Requires a TigerGraph Savanna or Community Edition instance with the `gsql`
CLI. See step 7.

## 9. MCP setup

Not wired up in this build (no MCP server available in the build
environment). `backend/app/graph_engine.py` is the integration point if you
add a TigerGraph MCP server later.

## 10. GraphRAG architecture

See `backend/app/rag.py` and the GraphRAG flow diagram in
`docs/ARCHITECTURE.md`. Retrieval is TF-IDF cosine similarity over
`data/sample/policies.json` and `data/sample/fraud_patterns.json`, combined
with graph-based similar-case retrieval
(`graph_engine.find_similar_historical_cases`). Swappable for a real vector
DB without changing the agent's interface.

## 11. Agent architecture

See `backend/app/agent.py` and the state-machine diagram in
`docs/ARCHITECTURE.md`. Hard safety rails: `MAX_INVESTIGATION_STEPS`,
`MAX_EVIDENCE_ROUNDS` (env-configurable) — the loop provably terminates.

GET  /api/investigations/{case_id}
GET  /api/cases

## 19. Limitations

- No live TigerGraph cluster or real IEEE-CIS dataset in this build — see
  the scope note at the top and `docs/ARCHITECTURE.md`'s real-vs-simulated
  table.
- Auth is a static API-key → role map, not full OAuth/JWT user management.
- Evidence-gathering, action execution, and the LLM explanation step are
  either mocked or optional by design (see the table in
  `docs/ARCHITECTURE.md`).
- Similar-case retrieval uses simple overlap scoring (shared device/IP/
  merchant), not learned embeddings.
- No CI pipeline is included (would be a `.github/workflows/tests.yml`
  running `pytest`; not created here since there's no repo/CI runner in this
  build environment to verify it against).

## 20. Future improvements

- Real TigerGraph deployment + `pyTigerGraph` wiring in `graph_engine.py`.
- Vector-embedding-based case similarity and policy retrieval.
- LangGraph-based agent for more complex branching/parallel evidence
  gathering.
- Real evidence channels (SMS/push step-up auth, core-banking block/freeze
  APIs) behind the same `mock_apis.py` interface.
- JWT-based auth with per-analyst audit attribution.
- React/Vite rebuild of the frontend if a component-based codebase is
  preferred over the current single-file dashboard.

## Implementation report

**What works (verified in this build, end-to-end, via real HTTP calls — not
just unit tests):**
- Full state machine: trigger → case creation → graph investigation →
  evidence gathering → deterministic risk scoring → uncertainty check →
  bounded evidence-gathering loop → next-best-action → human-approval gate →
  (simulated) execution → case resolution → memory update.
- Graph-based discovery of shared-device/shared-IP relationships and
  confirmed-fraud-history flagging, using real multi-hop traversal.
- Deterministic, itemized risk score (see `risk_engine.py`) — every point is
  attributed to a named piece of evidence.
- Policy-table-driven next-best-action selection, independent of the LLM.
- Human-approval gate: high-impact actions (`BLOCK_TRANSACTION`,
  `FREEZE_ACCOUNT`) are never auto-executed; `POST /approve` /
  `POST /reject` drive execution.
- Case persistence + full audit log (SQLite).
- GraphRAG-style retrieval over policy and fraud-pattern documents.
- Live dashboard, investigation detail view (evidence/graph/timeline/
  explanation/action), assistant chat grounded in real case state, and an
  admin/policy page — all calling the real API, not mock data.
- 22 automated tests, all passing.
- Benchmark evaluation script run against all 20 benchmark cases
  successfully (see below).

**What was tested:** risk engine edge cases (clean transaction, flagged
shared device, similar confirmed/cleared cases, large amount, score
bounding); policy engine's every branch (allow / monitor / step-up / block /
escalate); graph engine load integrity and no-invented-evidence guarantee;
full agent runs including approval and rejection paths; a live server smoke
test of `/api/health`, `/api/investigations`, `/api/cases`, `/api/cases/{id}
/graph`, `/api/chat`, and `/api/policies`.

**What is mocked:** step-up authentication, customer validation, analyst
information requests, and action execution (block/freeze/etc.) —
`backend/app/mock_apis.py`, clearly namespaced and documented. TigerGraph
itself is not connected; the in-memory graph engine implements identical
query semantics to the provided real GSQL.

**What requires TigerGraph credentials:** nothing, to run this prototype.
To move to a live TigerGraph cluster: `TG_HOST`, `TG_USERNAME`,
`TG_PASSWORD`, `TG_SECRET` in `.env`, plus wiring `pyTigerGraph` calls into
`graph_engine.py` (see step 7 above).

**What requires an LLM API key:** nothing is required — `ANTHROPIC_API_KEY`
is optional. Without it, explanations are produced by a deterministic
template that uses the same evidence and structure an LLM call would
receive. With it, `agent.py::_llm_explanation` calls the Anthropic API to
phrase the same structured facts more naturally, under a system prompt that
forbids inventing evidence.

**Benchmark results (last run, this build, synthetic data):**
```
total_benchmark_cases: 20
cases_completed: 20
average_investigation_steps: 13.1
average_response_time_seconds: 0.0051
explanation_completeness_pct: 100.0
unnecessary_evidence_requests: 0
action_distribution: {BLOCK_TRANSACTION: 18, REQUEST_STEP_UP_AUTHENTICATION: 2}
```
No ground-truth fraud labels exist in this dataset (matching the spec's
statement that the real dataset has none either), so precision/recall/F1
are not fabricated here — `evaluation/evaluate.py` computes them
automatically the moment real analyst-confirmed outcomes are supplied via
`_load_ground_truth()`. The 18/20 BLOCK rate reflects that the benchmark set
is deliberately the 20 *highest* bank-risk-score transactions in the sample
data (per the spec: "20 benchmark cases from the final two months" implies a
risk-skewed set) combined with synthetic hot-device/hot-IP sharing designed
into the sample generator — this is a property of the synthetic data, not a
tuned-to-look-good result; rerun `scripts/generate_sample_data.py` with a
different seed to see the distribution shift.
